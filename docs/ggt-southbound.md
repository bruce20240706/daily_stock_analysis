# 港股通（Southbound / GGT）呈现

Inc 2 在 HK 标的分析报告中新增「港股通」南向维度：确定性呈现港股通成份可买性、个股南向持股、市场级南向净流。

## 数据来源

- 免 token akshare 东财接口三个：
  - `stock_hk_ggt_components_em()` — 港股通成份榜单（全市场，代码列供归一比对）。
  - `stock_hsgt_stock_statistics_em(symbol="南向持股")` — 个股南向持股统计全市场日表（含持股数量/市值/占发行股百分比）。
  - `stock_hsgt_fund_flow_summary_em()` — 市场级沪深港通资金流汇总（4 行：`类型`=连接程序名 沪港通/深港通、`板块`=沪股通/港股通(沪)/深股通/港股通(深)、`资金方向`=北向/南向、`成交净买额`）。
- **真网已核验（2026-07-06）**：三个端点均可达、列结构与本地 inspect 一致——成份表返回 613 个成份（腾讯 HK00700 在内）、个股持股表返回腾讯占发行股 11.65% 真实行、净流表返回南向两腿（127+ 亿）。核验过程发现并修复了净流腿匹配缺陷（原按 `类型` 子串匹配，实际南向腿须按 `资金方向=南向` 判定，见下）。
- 三个端点彼此独立抓取、独立缓存、独立 fail-closed；一个端点失败不影响另外两个。

## 字段

| 字段 | 含义 | 单位 |
| --- | --- | --- |
| `eligible` | 港股通成份可买性（三态，见下） | bool \| null |
| `holding_shares` | 南向持股数量 | 股 |
| `holding_value` | 南向持股市值 | 元 |
| `holding_ratio_pct` | 持股数量占发行股百分比（**非**占 A 股口径） | % |
| `holding_trade_date` | 持股统计命中交易日 | YYYY-MM-DD |
| `southbound_net_flow` | 市场级南向净流（两腿之和） | 亿 |
| `southbound_flow_partial`（内部字段，不在报表中呈现） | adapter 内部仅单腿可得时标记（另一腿缺失，非零填充）；`_build_ggt_from_context` 不投影该键，`GgtContext` schema 无此字段 | bool |

全部 Optional / presence-only / None-tolerant。

## `eligible` 三态语义（fail-closed 核心）

- `True`：本股代码（经 `_ggt_key` 归一）出现在港股通成份表中。
- `False`：成份表**确已成功抓取**、行数 ≥ 50（截断守卫，见下）、且本股不在其中。
- `None`：成份名单**不可达**（抓取失败 / 空表 / 行数 < 50）——语义是「unknown」，**绝不**把 unknown 当作 `False` 呈现。三态互斥、互不覆盖。

## EOD 口径（重要边界）

南向持股与南向净流数据均为**日终（EOD）快照**，不做盘中实时更新。北向（HSGT）个股与市场级数据已于 2024 年被交易所永久停更（与 `docs/margin-trading.md` 记载的北向停更事实一致）；本文档仅覆盖仍在更新的**南向**（港股通）数据。

## 持股占比口径

`holding_ratio_pct` 取自原始列「持股数量占发行股百分比」——分母是**该股票的发行股本**，不是沪深 A 股整体占比、也不是自由流通盘占比。混用会导致数值解读错误。

## 净流口径与南向腿判定

- 市场级净流取「成交净买额」列（**不是**「资金净流入」列——两者口径不同，`stock_hsgt_fund_flow_summary_em()` 同时含这两类列，本功能只消费前者，混淆会导致数值对不上其他来源）。
- **南向腿判定（真网核验 2026-07-06 订正）**：主判据用语义列 `资金方向` 含「南」（南向=港股通流出至港），兜底退 `板块` 含「港股通」子串。**注意**：`类型` 列实际是**连接程序名**（沪港通/深港通，**不含**「港股通」子串），最初按 `类型` 子串匹配是错的——真网返回 0 命中 → 净流永久 `None`；已修正。北向腿（沪股通/深股通）资金方向为「北向」且板块不含「港股通」，天然被排除。
- 两条南向腿（沪+深）净买额之和；单腿缺失时另一腿仍参与求和并标记 `partial=true`；两腿皆缺失返回 `None`（NaN-first，不假零）。
- 单位为「亿元人民币」：真网核验 `资金净流入` 列 = 420，恰为港股通每日 420 亿元 **RMB** 额度（沪/深各 420 亿），故净流以亿元人民币计价（东财内部已 `/10000`）。
- **腿数 sanity（真网核验）**：真实表恰 4 行，南向仅 2 腿（沪港通南向 + 深港通南向），无聚合/合计行，`资金方向=南向` 判据不会 double-count。

## 缓存与 fail-closed

- **正缓存 12 小时**（`GGT_LIST_CACHE_TTL_SECONDS`，默认 43200 秒；日级数据，无需分钟级新鲜度）；**负缓存 300 秒**（抓取失败后短时间不重复对东财发起请求，避免死端点拖慢每次报告）。
- 三个端点（成份/持股/净流）各自独立维护缓存条目，互不影响。
- **min-row 截断守卫**：港股通成份表常年 500+ 行，若某次抓取返回 < 50 行，视为不可信响应（截断/半失败），按失败处理（负缓存 + `eligible=None`），不采信部分数据。
- **fail-closed**：东财不可达、超时、返回空表、解析异常 → 一律返回 `None`（对应 `eligible=None` / `holding=None` / `southbound_flow=None`），**绝不编造数值**、不拿旧缓存之外的默认值顶替。

## 抓取超时与冷缓存延迟

- 三个端点是**异构**的重量级东财接口（真网核验：成份 6 页分页 ~19s、个股持股全市场日表 ~10s、净流 ~0.5s），显著慢于常规实时报价抓取。故 GGT 用**独立**的 per-leg 超时 `GGT_FETCH_TIMEOUT_SECONDS`（默认 20 秒/腿），比 `fundamental_fetch_timeout_seconds`（3 秒）宽松——否则冷缓存下慢腿必超时、报告永远只显示「成份状态未知」。
- **各腿独立**受超时上限（非共享 deadline）：慢的成份腿不会饿死快的净流腿。任一腿真正挂起（网络库无超时）也会在 per-leg 预算耗尽后被后台线程 abandon，调用方按时释放，该腿降级为 `None`（G8 有界超时护栏），不阻塞其余两腿、不拖垮 HK 分析线程。
- **冷缓存一次性成本**：某个 12 小时窗口内首个 HK 报告触发三腿冷抓（合计 ~30 秒串行），写入 12 小时缓存后同窗口后续 HK 报告全部命中暖缓存、即时返回。批量日更（systemd）下该成本按天摊薄一次。

## 门控与语义

- **仅 HK 标的**（港股）触发；A 股/美股/crypto 无该 section。
- **presence-only**：GGT 块在 `data_perspective.ggt_context` 中，成功抓到至少一项才出现；三项数据面独立展示，某一项失败不影响另外两项。
- **纯展示、不影响决策**：不喂 LLM prompt、不进 `decision_stability`、不产生任何 bias、对信号/回测完全只读（与融资融券章节记载的分析原则一致）。

## 看板可买性注解（Inc 2b，已落地）

信号看板每行呈现港股通可买性 eligibility 三态徽章（`True`→「港股通」/ `False`→「非港股通」/ `None`→无徽章）。**实现要点**：看板 `GET /api/v1/signals/board` 在 uvicorn 请求内按需计算（无 systemd/scheduler 预计算），故在**同一进程内自抓**一次全市场 eligibility set（`get_ggt_eligibility_set`，有界、进程级 12h 缓存），对每个 `market=="HK" and status=="ok"` 的行做成员判定 —— **不需要跨进程共享缓存**（早期 defer 论据基于「看板刷新与报告生成运行在不同进程、模块级缓存互不可见」的前提，经核实看板与报告同为 uvicorn 进程内计算，该前提不成立）。只呈现 eligibility；个股持股/市场级净流仍仅在报告 section 呈现，看板不注解这两项。HK ETF（如 2800.HK）不在成份表中，镜像报告口径判定为 `False`。

## 不动的既有行为

北向（HSGT）停更事实、A 股融资融券、资金面 capital_flow、龙虎榜、主力资金流、换手率/量比/筹码等既有 section 全部零改动。

## 配置

- `GGT_LIST_CACHE_TTL_SECONDS`（默认 43200 秒 = 12 小时，最小钳制 60 秒；仅 env，**不进** `config_registry` / Web 设置页 / locale，沿用 `VPS_*` 系列 env-only 惯例）。
- `GGT_FETCH_TIMEOUT_SECONDS`（默认 20.0 秒 = 单腿抓取上限，最小钳制 1.0 秒；仅 env，不进 `config_registry`）——见「抓取超时与冷缓存延迟」。

## v1 已知局限

- 仅最新可得的持股/净流快照，无趋势/多日序列。
- 无专用 Web 组件（同融资融券/资金面，经 notification markdown + 报告 payload 呈现）。

## 真网验证结果（2026-07-06 于 eastmoney 可达环境完成）

三个 probe + 净流币种/量级/腿数 sanity 已在关沙箱前台环境实测，结论如下（发现并修复 2 处缺陷，见「净流口径与南向腿判定」「抓取超时与冷缓存延迟」）：

1. 三个 probe（经 adapter 公开方法、canonical 输入直连真实端点）：
   - `get_ggt_eligibility_set()` — ✅ 成份表可达，返回 613 个成份，列结构与 inspect 一致，腾讯 `HK00700` 在集合中（经 `_ggt_key` 归一命中）。
   - `get_ggt_holding("hk00700")` — ✅ 持股统计表可达，列名未漂移，查到腾讯真实行：占发行股 `11.65%`。
   - `get_southbound_flow()` — ✅ 净流表可达，真实 4 行、南向恰 2 腿（沪港通南向 + 深港通南向）。**发现缺陷**：南向腿须按 `资金方向=南向` 判定，`类型` 列实为程序名（沪港通/深港通，不含「港股通」子串）——原按 `类型` 子串匹配命中 0 行导致净流永久 `None`，已改按语义列并核验修复（返回 `127+ 亿`）。
2. 端到端：`get_ggt_context("hk00700")` 冷缓存串行抓三腿，三腿 `status=ok`、真实数值齐全，presence-only 门控按预期工作。**发现缺陷**：异构端点（成份 ~19s / 持股 ~10s）远超默认 `fundamental_fetch_timeout_seconds`（3 秒）→ 冷缓存下慢腿必超时空返，已新增 `GGT_FETCH_TIMEOUT_SECONDS`（默认 20 秒/腿、各腿独立）修复。
3. 净流币种 + 量级 + 腿数 sanity — ✅ 币种为**亿元人民币**（`资金净流入` 列 = 420，恰为港股通每日 420 亿元 RMB 额度）；量级为亿元级（南向净流 `127+ 亿`）；腿数恰 2（无聚合/合计行，`资金方向=南向` 判据不 double-count）。
